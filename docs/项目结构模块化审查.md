# 项目结构模块化审查

审查日期：2026-09-23　分支：`test-2`　范围：`src/` 全部代码目录与仓库根目录（不含 `node_modules`、`src/assets` 内的美术文件本身）
方法：静态扫描目录树、文件数量和导入关系。没有运行构建。

## 一、结论

**未达标。** 细分到组件这一级，模块化做得很好：超过 500 行的文件为 0，底层依赖方向单向，UI 组件大多是"一个组件一个目录 + index 出口"。但**越往上层目录越模糊**：`engine`、`data`、`store` 三个核心层的根目录都平铺了 28～49 个文件，还和子目录混放；UI 中间层"有的分组、有的不分组"，存在同名文件与同名目录并存、同一概念散在多处、跨功能区共用组件放错位置等问题。

| 维度 | 评级 | 说明 |
| --- | --- | --- |
| 单文件体量 | ✅ 达标 | 源码最大 494 行（`engine/battle.ts`），没有文件超过 500 行 |
| 顶层依赖方向 | ✅ 达标 | engine 不依赖 data、explore、store、ui；store 不依赖 ui |
| 组件原子化 | 🟡 基本达标 | 组件基本做到一个组件一个目录，但部分组件目录内平铺了 15～32 个文件 |
| 目录职责单一 | ❌ 不达标 | 36 个目录同时放了散落文件和子目录 |
| 目录平铺规模 | ❌ 不达标 | 17 个目录的平铺文件超过 12 个，最多的有 49 个 |
| 概念唯一归属 | ❌ 不达标 | 遗物、物品、卡牌等概念分散在 3～4 处 |

## 二、判定标准（本报告采用的"极致模块化"定义）

1. **目录职责单一**：一个目录要么是**容器**（只放子模块目录，再加一个可选的 `index.ts`），要么是**模块本体**（只放实现文件，最多再加一个 `parts/` 子目录）。不允许"散落文件 + 若干子目录"混放。
2. **平铺上限**：模块本体目录的平铺文件不超过 12 个（`.tsx` 和同名 `.module.css` 算作一组）。超过就按子职责拆出子目录。
3. **不允许同名文件与同名目录并存**：`x.ts` 与 `x/` 不能同时存在，入口统一为 `x/index.ts`。
4. **一个概念只在一处**：同一个业务概念（遗物、物品、卡牌……）在每一层只有一个目录，跨层按"层/概念"对称命名。
5. **跨功能区共用的组件放在共享层**：被两个以上功能区引用的组件，不能留在其中某一个功能区里。
6. **命名规则统一**：组件目录用大驼峰（PascalCase），逻辑目录用小驼峰（camelCase）；跨模块导入统一用 `@/`，模块内部导入用 `./`。
7. **src 只放代码和资源**：文档、提示词放到 `docs/` 或 `design/`。

## 五、整改路线（建议顺序）

1. **第一步（纯移动，风险低）**：消除同名文件与同名目录并存；把 src 里的 md 文档移出去；清理根目录临时产物和多余的锁文件。
2. **第二步**：拆分 `engine/`、`store/`、`data/` 的根目录（按第三节的分组表），同时统一跨模块导入为 `@/`。
3. **第三步**：遗物、session、rules 等同一概念在各层收拢并改名。
4. **第四步**：把 `ui/common` 按族群分组，把 HandCard、DeckCard、EnemySprite 移到共享层，把 `ui/battle` 的 Victory、Rail、choreo 归组。
5. **第五步**：给平铺超过 12 个文件的组件补上 `parts/`，清理容器目录里的零散文件。
6. **收尾**：更新 `docs/code-map/`，并考虑加一条 ESLint `import/no-restricted-paths` 规则，把"依赖方向"和"目录规范"固化下来。
